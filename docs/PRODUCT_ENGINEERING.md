# 实现与学习记录

本轮使用 Python / FastAPI / Pydantic / HTTPX / SQLite / 原生 JavaScript ES modules。前端运行不需要 Node 构建；Node 只用于语法检查和固定版本 Prettier 格式化。设计依据来自已安装的 ui-ux-pro-max 与 Impeccable。没有为了增加框架名称重写服务。

一个具体例子：用户保存“CSV 少最后一行”报告后，另一个页面又补充了操作记录。第一个页面的确认携带旧 revision，数据库条件更新命中0行，于是返回409。浏览器保留自己的草稿，读取最新版本后让用户明确选择合并方向。这里 revision 是乐观锁，解决的是“后保存的人悄悄覆盖前一个人”，不是数据库密码或分布式锁。

再看历史恢复：旧版本仍保持原样，恢复创建一个更高 revision，确认字段清空。这能同时回答“我现在看到什么”和“过去发生了什么”。版本快照与当前记录在同一个事务里保存，否则可能发生当前内容更新但历史没写入的半成功。

AI 整理只做选行、分类和建议追问。程序按行号取原文并核对引用，不把模型输出的描述直接当成事实。用户修改后的四栏是 reviewer draft，原始 analysis 保持不变。这避免了“用户改对之后，把模型之前的错误抹掉”。但是引用对不代表分类对；模型质量仍要逐例检查，测试替身不能算真实AI评测。

失败恢复的例子：模型运行中允许停止；上次服务被关掉，操作表下次启动显示 interrupted；网络故障时原草稿还在。接口不会自动无限重试，因为重复模型请求既可能浪费资源，也不能证明旧请求没有完成。模型分析不持有数据库写锁；推理完成后再做版本检查。

SQLite 在本产品中是明确选择：单人、单服务、短事务、小文本。WAL 可让读者继续读取已提交快照，写者仍然串行。高并发读取短测通过，不代表可以部署多人平台；若改为多人、多实例，需要重新设计身份隔离、任务所有权和数据库部署。

验证入口：`python scripts/check.py` 使用隔离环境；`python -m reprolens.database check/backup/restore` 核查实际SQLite；`/api/health` 是活着，`/api/ready` 是核心数据库流程可服务；Egolite 实际点击和截图验证用户是否能完成任务。单独检查 DOM 中有按钮并不能证明交互可用。本轮截图发现侧栏项目被 flex 压缩重叠，实际填表发现首次修改确认报告会重建输入框，两者都在复验前修正。

面试可追问：

1. 为什么模型推理不能放在 SQLite 写事务里？它会怎样影响其他保存请求？
2. HTTP 超时后能否直接重试创建？请求 ID 如何绑定参数？
3. 为什么恢复历史也需要重新确认，而不是把旧的 confirmed 原样复制？
4. WAL 解决了哪些并发问题，哪些没有解决？
5. 一个精确引用且 JSON 合法的模型结果，为什么仍可能完全不可用？
6. 如何证明“没有明显持续内存增长”？为什么500次循环仍不能证明永远不会泄漏？

这些说明属于开发文档，不出现在工作台主流程。
